# The tile layer

This document describes the tile layer of `MojoProof/Tile/` (namespace `MojoProof.Tile`): a
small language of tile programs over tensor cells, its interpreter, and the theorems that
relate a kernel's compiled code to a tile program. The Lean statements are the reference; the
instances and the tests are in `MojoProofTest/Tile.lean`, `MojoProofTest/TileNaive.lean`,
`MojoProofTest/TileGrade.lean`, `MojoProofTest/TileMatVec.lean` and
`MojoProofTest/TileLanes.lean`.

## 1. What the layer is

* **Programs.** A tile program `Prog E α` is a finite tree of events of a signature `E` (a type
  of events and, for each event, the type of its answer): `ret a` ends with `a`, and `vis e k`
  performs the event `e` and continues with `k` applied to the answer. Every program is a finite
  tree, so every run ends; there is no loop construct, no coinduction and no library of effect
  handlers. `Prog E` is a monad (`Prog.bind`).
* **Events** (`TileE V`, over cell values `V`): `load b c` reads cell `c` of buffer `b`,
  `store b c v` writes `v` there, `choose s` asks for the number of a float choice at the site
  `s`, `barrier` ends a phase, and `ub msg` stops with undefined behavior.
* **Float sites are semantic.** A `Site` is a thread, a cell, a float operation (`FBinOp`) and
  the term of a reduction it is for (0 for an element-wise operation). It never names a
  compiled position: the step at which a kernel's thread performs that operation is computed
  from the kernel's paths (`siteStep?`) and checked (it must be the same on every path that has
  the operation), and the oracle of the kernel translates to the tile oracle through it
  (`oracle`).
* **The interpreter** (`run1`, `runAll`) handles the events: faults (a load of a cell that was
  never set, and `ub`, stop the run with `Sem.Fault.ub`), float choices (the tile oracle's
  number for the site), memory (a cell map per buffer) with an access log (thread, buffer,
  cell, read or write, phase of every access) and phases (`barrier` advances the phase number
  that the log records). `runAll` runs threads `0` to `T - 1` in turn.

The answer of a float choice is the raw oracle number, which the program decodes as the LLVM
semantics does: it delivers a NaN result at the number divided by 3 (Sem's `deliver`, the same
function the LLVM semantics applies to a float operation's result), and the remainder modulo 3
chooses a contraction (`dotStep`). So the tile oracle that a kernel's oracle gives is the
kernel's oracle at the site's thread and the computed step, unchanged, and a tile program and
the kernel deliver a NaN from the same number in the same way.

## 2. The value type

`Prog`'s values are concrete: a cell holds a value of the type `V` (FloatLib's `Model ft.fmt`
for a float buffer), and the events answer concrete values. They are not symbolic terms.

The reason: a tile program then runs, so a program can be evaluated on concrete inputs by
`decide +kernel` or `#eval`, and a wrong program is refused by evaluation (section 5). The
generality is in the theorems instead: they quantify over every input tensor, every count and
every oracle. A symbolic value type would need a second evaluator of terms, next to the one that
already checks the compiled code (`MojoProof/Sym/`), and there is to be one semantics of LLVM.

## 3. What is proved

* `map2_run`: for every float format, binary float operation with an IEEE operation (`fbin`),
  count `n` at most the length `N` of the tensors `x` and `y`, tile oracle and number `T` of
  threads, the element-wise program `map2 op n` (thread `k < n` loads cell `k` of buffers 0 and
  1, asks for the choice at site (`k`, `k`, `op`, 0) and stores the delivered result in cell `k` of
  buffer 2; the other threads do nothing) runs from `inputs x y` (buffers 0 and 1 hold `x`
  and `y`) without a fault, leaves buffers 0 and 1 as they were, and its buffer 2 holds at
  every cell `k < n`, `k < T` the operation on `x_k` and `y_k` delivered at the site's
  number.
* `map2_refines`: for every kernel whose theorem is the conclusion of `mojo_kernel`'s `map2`
  clause (`Kernel.Sound` for `Elem.Out` with the bytes `Elem.map2` of a float operation at the
  oracle numbers of a step `s`, the result of `Kernel.sound_map2`), and every path list whose
  computed step for that operation is `s`, every observation of a complete run of the kernel
  (`Kernel.Obs`, every admitted address choice and oracle `ω`) holds at the output cell of
  every thread `k < n`, `k < T` the value of cell `k` of buffer 2 of the run of `map2 op n`
  under the translated oracle `oracle paths ω`. It covers every kernel of the clause; the
  kernel's oracle numbers enter only through the computed step.
* The instances for `vector_addition`, `vector_multiply` and `vector_subtraction`
  (`vadd_tile`, `vmul_tile`, `vsub_tile` in `MojoProofTest/Tile.lean`) are generated by the
  test command `tile_map2`, which states the theorem once and proves it by `map2_refines` applied
  to the kernel theorem `mojo_kernel` generated, the step of the operation evaluated by the
  kernel; each covers that one kernel at every valid one-dimensional launch, alignment, memory,
  count, input and oracle of its theorem's premises. Each is also applied at two concrete launch
  sizes, 6 threads and 2 threads, with a memory and a pair of inputs.
* `dot_run` (`MojoProof/Tile/Dot.lean`): for every float format, contraction flag `c`, sizes
  `m`, `p`, `K` with `K` at most the row lengths `sA` and `sB`, matrices `A` (`m × sA`) and `B`
  (`p × sB`), tile oracle, number `T` of threads and placement `rc` of threads on cells with no
  two threads at one cell, the matrix product `dot c K rc` (thread `t` at cell `(r, col)` loads
  cells `(r, j)` of buffer 0 and `(col, j)` of buffer 1 for `j < K`, asks for the `fmul` and the
  `fadd` choice of each term, folds `dotStep` from `+0` and stores the result in cell
  `(r, col)` of buffer 2; cells of two coordinates are numbered by `Nat.pair`) runs from
  `mats A B` without a fault, leaves buffers 0 and 1 as they were, and holds at the cell of
  every placed thread `t < T` the `dotLoop` over the first `K` pairs of row `r` of `A` and row
  `col` of `B` at the thread's oracle numbers.
* `dot_meets`: every such cell meets TorchLean's product (`Meets`): when no round is fused, the
  word and entry `(r, col)` of `Tensor.matmul` of the first `K` columns of `A` and the transpose
  of the first `K` columns of `B` are the same word or both NaNs, and when the format is IEEE
  and the word is finite, it is within `dotBound` of the real product, and when the format is
  IEEE it is `GPUProof.Approx` at `GPUProof.dotGrade` of every exact row and column and grades at
  which the cell's inputs are `GPUProof.Approx` (`meets_dotLoop`, from `matmul_cols_nanEq`,
  `matmul_cols_error` and `MojoProof.Sem.dotLoop_approx`).
* `mat_refines` (`MojoProof/Tile/Mat.lean`): for every kernel that is sound (`Kernel.Sound`) for
  `Elem.Out` at the cells `(row * sC + column) * w` with the bytes `matBytes` (the encoding of
  each in-bounds thread's `dotLoop` at its oracle numbers `o k`; the shape of
  `Kernel.sound_mat`'s conclusion), every launch valid with `z` sides 1, layout, float type of
  stored size `w`, flag, oracle numbers, sizes with `p ≤ sC` and matrices: in every observation
  of a complete run, the run of `dot c K (place L m p)` (each in-bounds thread at its row and
  column) at the tile oracle `pairOracle o` ends without a fault, and every cell in bounds and in
  the launch's window is computed by one thread whose output cell holds (`Elem.word`) the word at
  that cell of buffer 2, a word that meets the product. It covers every kernel with such a
  theorem.
* `naive_tile` (`MojoProofTest/TileNaive.lean`): `mat_refines` at the theorem `NaiveFam.sound`
  of the naive matmul kernel's row-stride family `NaiveFam.prog sA sB sC`, its bytes being
  `matBytes`'s (`bytes_eq`). It covers the family at every row stride, every launch valid with
  `z` sides 1, every memory of `Mat.Pre`, sizes below `2 ^ 31` and every `K ≤ min sA sB`; the
  compiled kernel is the family at the strides 768, 768 and 50257. The tile
  oracle is `pairOracle` of the kernel's oracle numbers at its loop's steps (`NaiveSpec.o`), which
  are taken from the kernel's specification, not computed from its paths as `siteStep?` does for
  `map2`.
* `meets_holds`, `mat_holds` (`MojoProof/Tile/MatVec.lean`): a matrix product whose second
  matrix has one row is a matrix-vector product. For every IEEE format and width, words that meet
  the product at the cells `(i, 0)` meet the rule of
  `GPUProof.Spec.matVec GPUProof.matVecGrade` at the uniform encoding `matVecEnc` and the inputs
  read from the matrices (`matIn`); and so does every kernel of
  `mojo_kernel`'s `mat` clause whose second matrix has one row, at its observed memory: in every
  observation `Bk` of a complete run, the floats of `Bk`'s output block at the rows' cells
  `i * sC * w` (`Elem.word`) meet the rule (docs/proofs/spec.md, step 9). The words come from the
  kernel's soundness and the observation, the rule from `Meets`; the tile run that computes the
  same words is `mat_refines`'. Its instance is `naive_holds` (`MojoProofTest/TileNaive.lean`):
  the naive matmul kernel with one column, at every launch valid with `z` sides 1 that covers the
  rows and column 0, every memory of `Mat.Pre` and sizes below `2 ^ 31`.
* `MatSetup`, `kernelRows`, `kernelRows_meetsAt`, `kernelRows_nonempty`
  (`MojoProof/Tile/MatVec.lean`): a kernel's behaviors on a matrix-vector product's inputs are the
  observed words of its runs. For every kernel, layout, float type, width and setups (launch,
  arguments, caller memory, admission, output block and row stride) whose matrices' inputs are
  the input words (`matIn`), `kernelRows` is the set of the floats of the output block at the
  rows' cells in the observations of admitted complete runs; when every setup has `mat_holds`'
  premises (`MatSetup.Fits`) it meets `GPUProof.Spec.matVec GPUProof.matVecGrade` at `matVecEnc`
  (`GPUProof.MeetsAt`), and a fitting setup with an admitted choice and oracle gives a behavior
  (`Kernel.Sound.exists_obs`). The design is in docs/proofs/spec.md, step 9. Its instance is
  `naive_meetsAt` (`MojoProofTest/TileNaive.lean`): the naive family's setups `naiveSetups` at
  every row stride fit (`naive_fits`).
* `stride_approx`, `bfly_approx`, `groupDot_approx`, `groupDot_holds`
  (`MojoProof/Tile/MatVec.lean`): for every IEEE format, flag and oracle sequences, loops over
  the pairs strided by the lane count and added along any tree over the lanes, every lane of a
  butterfly over `2 ^ k` such loops, and so `MojoProof.Sem.groupDot k`, are `GPUProof.Approx` at
  `GPUProof.laneGrade` at the tree's depth (`k` for the butterfly) and `⌈n / W⌉` pairs per lane;
  `groupDot k` per row meets the rule of
  `GPUProof.Spec.matVec (GPUProof.laneVecGrade (2 ^ k) k fun n => ⌈n / 2 ^ k⌉)`, the case of
  `rowTrees_meetsAt` below at lane 0's butterfly tree. They are about words, not about a kernel's
  run (docs/proofs/dot.md, statements 15-16).
* `bflyDeliver_holds`, `bflyRoundsAt_take_succ`, `bflyRoundsAt_chain`
  (`MojoProof/Tile/MatVec.lean`): for every IEEE
  format, width, `k`, flag, oracle sequences and oracle numbers per round and lane, lane 0's
  word after the semantics' rounds `bflyRoundsAt (fun r l x y => deliver (Model.add x y)
  (ob i r l)) (bflyOffsets k)` over the lanes' strided loops meets the rule of
  `GPUProof.Spec.matVec (GPUProof.laneVecGrade (2 ^ k) k fun n => ⌈n / 2 ^ k⌉)`, since it is
  `groupDot k`'s word or both are NaNs (`MojoProof.Sem.bflyDeliver_nanEq`); and for every
  carrier and combination the value after the first `r + 1` rounds is round `r`'s combination
  of the lane's and its partner's values after the first `r`. For every type, round function,
  offsets and set of lanes that holds each round's partners, values per round and lane of which
  each, at every lane of the set, is the round function of the lane's own and its partner's
  values the round before are the rounds over the first `r` offsets from the first values, at
  every lane of the set (`bflyRoundsAt_chain`, by induction on `r` with
  `bflyRoundsAt_take_succ`): the lanes' partner chain, closed over all the lanes at once. Tests
  (MojoProofTest/TileBfly.lean) at 4 and 8 lanes with the round function `a ++ b` on lists of
  lane numbers, which tells two orders of the offsets apart: `chain4` over `bflyOffsets 2`,
  `chain8` over `bflyOffsets 3` and over `1, 4, 2`, with their round premises by `decide`; and
  `mutant4`, `mutant8`, the offsets reversed, where the round premise and the rounds' value both
  fail. They are about words; the gemv_kernel tests that use them are in docs/proofs/spec.md.
* `rowTrees`, `rowTrees_meetsAt`, `rowLoops`, `rowLoops_meetsAt` (`MojoProof/Tile/MatVec.lean`):
  strided lanes added along a tree per row. For every IEEE format, width, lane count `W`, tree
  `t` whose leaves are the lanes, each once, and flag, the behaviors whose output `i` is
  `MojoProof.Sem.treeDot t` over the lanes' loops on the pairs of row `i` strided by `W` meet
  `GPUProof.Spec.matVec (GPUProof.laneVecGrade W t.depth fun n => ⌈n / W⌉)` at `matVecEnc`
  (`GPUProof.MeetsAt`, by `stride_approx`); `groupDot k` per row is a behavior at lane 0's
  butterfly tree. `rowLoops` is `rowTrees` at one lane and the tree `.leaf 0`: output `i` is a
  `dotLoop` from `+0` over row `i` and the vector, by `treeDot`'s definition at a leaf and
  `stride_one` (the one lane's strided list is the whole list); `rowLoops_dotLoop` states the
  direction the tests use, that every such loop per row is a behavior. `rowLoops_meetsAt`, that it
  meets `GPUProof.Spec.matVec GPUProof.matVecGrade` at `matVecEnc`, is `rowTrees_meetsAt` there. The
  two grades differ by definition, lane length `⌈n / 1⌉` against `n`, and are equal at every `n`
  (by `n + 1 - 1 = n` and `n / 1 = n`, in the proof); the equation enters through
  `meetsAt_grade`, since a rewrite of the grade inside `GPUProof.MeetsAt` is not type correct.

## 4. Trust

The tile layer is not in the trusted base. Its programs and its interpreter are definitions
that a theorem relates to the LLVM semantics: a statement about a kernel holds of the kernel's
compiled code whether or not the tile program is the intended one, and the headline theorems
about kernels remain stated against `Kernel.Obs` and TorchLean tensors. A wrong tile program
makes `map2_refines` or `mat_refines` inapplicable (its premises fail), not a wrong theorem true.

## 6. Scope and what is not done

* Element-wise programs of one binary float operation per thread and the matrix product of one
  dot loop per cell are related to kernels. Phases across threads, shared memory and collectives
  are not; `barrier` is handled only as a phase number in the log.
* The steps of a loop's float operations are not computed from a kernel's paths: `mat_refines`
  takes the kernel's oracle numbers per term (`o`) as they appear in its theorem, and only one
  kernel, the naive matmul, is an instance.
* Cells are numbered within a buffer; coordinates through a layout of the layout model are not
  used yet.
